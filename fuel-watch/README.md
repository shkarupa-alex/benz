# Fuel Watch skill

## Сборка и установка

Репозиторий — единственное место, где нужны `npm` и `node_modules`. Перед публикацией skill выполняется:

```bash
npm ci --ignore-scripts
npm run build
npm test
npm run test:dist
```

Hermes должен синхронизировать весь каталог skill вместе с committed `dist/`. На целевой машине Fuel Watch запускается только через `dist/scripts/*.mjs`; `npm install` там не нужен и запрещён инструкцией skill. Внешняя команда `agent-browser` остаётся отдельным runtime prerequisite и никогда не устанавливается самим skill.

## Постоянные данные

Установленный каталог skill считается read-only и полностью заменяемым. Все изменяемые данные находятся вне него:

- `~/.fuel-watch/config/config.json` — пользовательские настройки, создаются из шаблона только при первом запуске;
- `~/.fuel-watch/config/agent-browser.json` — пользовательский browser config;
- `~/.fuel-watch/history/` — история наблюдений (`history.retentionDays`, по умолчанию 90 дней): `history.json` — маленький manifest, `history.ticks/ГГГГ-ММ-ДД.jsonl` — по строке на опрос в файле за UTC-сутки, `history.stations.json` — названия и адреса АЗС один раз, а не в каждом опросе. Истекшие сутки удаляются целым файлом. История формата v1 (один JSON) конвертируется при первом сборе под lock, оригинал остаётся в `history.v1-backup.json`. При ~80 АЗС это порядка 15–25 КБ на опрос: шесть фоновых сборов в день — около 10 МБ за 90 дней, каждый час срочного мониторинга раз в 10 минут добавляет ещё ~6 опросов; прогноз на каждом сборе читает только последние 28 дней (около секунды и 300 МБ памяти на запись опроса);
- `~/.fuel-watch/state/latest.json` — последний snapshot, continuity идентичности и coverage-baselines;
- `~/.fuel-watch/monitors/<id>/` — транзакционное состояние активных мониторов.

Повторная синхронизация skill не перезаписывает эти файлы. Для изолированного окружения весь корень можно изменить переменной `FUEL_WATCH_HOME`; отдельно путь истории — `FUEL_WATCH_HISTORY_PATH`.

При первом запуске существующая история из прежнего default path `~/.local/state/fuel-watch/history.json` (или `$XDG_STATE_HOME/fuel-watch/history.json`) копируется в новый каталог без удаления оригинала и только если новая история ещё не создана.

Частоты — пользовательские настройки (5–1440 минут), а не часть immutable skill-пакета:

- `monitoring.intervalMinutes` (шаблон: 10) — частота мониторинга в задаче, режим «надо срочно заправиться», который агент ведёт по просьбе пользователя;
- `history.sampleIntervalMinutes` (необязательная) — обычный промежуток между тиками истории, то есть частота фонового сбора. Прогноз и статистика считают пропуск длиннее трёх таких промежутков дырой в данных; пока она не задана, вместо неё берётся `monitoring.intervalMinutes`, что подходит только истории из одного мониторинга в задаче. Установщик timer без неё не работает.

Шаблон конфига задаёт `history.retentionDays: 90`, но уже созданный `~/.fuel-watch/config/config.json` при обновлении skill не меняется: на существующей установке значение нужно поднять вручную (допустимо 7–365).

## Фоновый сбор на Linux

Для долгой статистики сбор должен идти по расписанию без агента; агент (Hermes) только читает историю через `dist/scripts/history-stats.mjs`.

Требования на сервере: Node.js 22+, `agent-browser` в PATH (ставится отдельно, skill его не устанавливает) и пакет `xvfb`, если нет display: браузер работает только headed, Xvfb agent-browser поднимает сам — `xvfb-run` не нужен.

Для прогноза хватает шести сборов в день. В пользовательском конфиге `~/.fuel-watch/config/config.json` задайте `"history": { "retentionDays": 90, "sampleIntervalMinutes": 175, ... }` (до первого сбора его ещё нет: скопируйте туда шаблон `dist/config/config.json` из skill; сам шаблон в каталоге skill не правьте — он перезаписывается при синхронизации) и установите timer:

```bash
sh <каталог skill>/deploy/linux/install-systemd-user.sh --on-calendar "*-*-* 07,10,13,16,19,22:30:00"
```

Установщик сверяет расписание с интервалом через `systemd-analyze calendar` и отказывается, если обычный шаг расписания больше 2,5 × `history.sampleIntervalMinutes` (запас на случайную задержку timer и ожидание чужого сбора). 175 минут — чуть меньше трёх часов между дневными сборами, поэтому ночной перерыв 22:30 → 07:30 (9 ч) всегда больше трёх промежутков и честно считается дырой, а не перебоем, «закончившимся» в 07:30. Время — местное время сервера. Без `--on-calendar` timer срабатывает каждые `history.sampleIntervalMinutes`; первый запуск — через один интервал после установки, а не сразу. Без `history.sampleIntervalMinutes` установщик отказывается работать: иначе timer шёл бы с частотой срочного мониторинга (каждые 10 минут — 144 полных опроса в день), а фиксированное расписание сверялось бы с чужим интервалом, и каждый трёхчасовой шаг выглядел бы дырой в данных.

Скрипт ставит `~/.config/systemd/user/fuel-watch-collect.{service,timer}` (Type=oneshot, таймаут 25 мин с учётом ожидания чужого сбора, `Nice=10`, путь к skill и `PATH` фиксируются в unit) и включает timer. Если `node` установлен через nvm, у которого нет стабильного пути, unit на каждом запуске подгружает `nvm.sh` и берёт версию из алиаса `default`, так что обновление Node его не ломает; каталоги `versions/<v>/bin` в unit не попадают, а установщик заранее проверяет, что `default` — Node 22+ и с ним находится `agent-browser`. После смены расписания или интервала скрипт нужно запустить повторно; drop-in каталоги `fuel-watch-collect.*.d` перекрывают то, что он ставит, и он об этом предупреждает. Чтобы timer работал без активного входа пользователя: `sudo loginctl enable-linger <user>`. Удаление — `--uninstall` (история остаётся), предпросмотр unit — `--print`.

Обёртка `deploy/linux/fuel-watch-collect.sh` пишет в journal одну строку на запуск (вердикты, статусы источников, коды предупреждений) и возвращает код collector: код 2 (ни одного источника) и 75 (`CLEANUP_FAILED`) видны как failed unit. Без systemd её можно вызывать из cron по тому же расписанию.

Timer нужен для истории; срочный поиск заправки агент по-прежнему ведёт мониторингом в задаче с `monitoring.intervalMinutes`. Сборы не пересекаются: `collect.mjs` ждёт окончания уже идущего сбора (до 10 минут, затем `COLLECTION_BUSY`) и выдерживает после него минимум минуту, поэтому tick, совпавший с timer, просто начнётся позже. На «что сейчас» агент отвечает свежим `~/.fuel-watch/state/latest.json` или разовой проверкой (см. SKILL.md). Частота опроса — нагрузка на источники: каждый сбор — полный опрос всех источников с одного IP. Если источник начинает отказывать в соединении или выдавать `CHALLENGE`, его можно временно выключить в `sources[].enabled` пользовательского конфига, а не учащать попытки.

## Полевые сверки

Наблюдения ниже — разовые проверки, а не долговременный рейтинг источников.

- 31 августа 2026, Рокоссовского, 1Р: реальное возобновление продажи 92/95 примерно в 12:20–12:40 после прибытия бензовоза около 11:30. Лучше всего событие отразил Benzonavt (включая доступную человеку историю), затем gdebenz; 2GIS был полезен как дополнительный текущий сигнал, Yandex хуже всего подходил для временной сверки из-за отсутствия grade-specific freshness metadata.

Новые ручные сверки следует добавлять отдельными датированными пунктами с фактическим состоянием, временем проверки и показаниями всех источников.

## Что источники публикуют помимо наличия

Живая проверка контрактов 21 сентября 2026 года на всех четырёх источниках:

- **Каталог марок станции.** `station.fuel_assortment` у 2GIS, `fuels` у Benzonavt, `meta.f` у gdebenz (заполнен не у всех строк). Yandex каталог не публикует: его `fuelAvailability` описывает марки, по которым есть данные о наличии, а не ассортимент, поэтому выводить каталог из него нельзя. В живом прогоне каталог был известен у 30 АЗС из 74; отсутствие каталога трактуется как «неизвестно», а не «не продают».
- **Лимиты литров.** `fuel_statuses[].limit_liters` и станционный `limit_liters` у 2GIS, `limits[]` (марка, литры, `since`) в detail-ответе Benzonavt, текст `Лимит N л` в карточке gdebenz. В отчёте показывается минимальный известный лимит на АИ-95. Два времени у лимита означают разное и обрабатываются по-разному: `observedAt` (у gdebenz — `last_at` строки) — это когда лимит видели, такой лимит истекает по общему окну свежести и печатается с возрастом, если он уже не свежий; `inForceSince` (у Benzonavt — `limits[].since`) — это когда лимит начал действовать, и он остаётся в силе сколь угодно долго. Живой detail-ответ Benzonavt 21 сентября 2026 года содержал в одном ответе лимиты с `since` от 21 и от 17 сентября — оба действующие, поэтому читать `since` как возраст наблюдения нельзя. 2GIS лимиты вообще не датирует и публикует их рядом с текущим статусом, поэтому возраст у них не выдумывается.
- **Метрики доверия источника.** `confidence_base`/`confirmations`/`svc` и поля автора комментария у gdebenz, `st.confidence`/`confirmations`/`reports`/`basis` и `reports_24h` у Benzonavt, `reports_count` у 2GIS. Сохраняются как provenance в поле `trust`; в уверенность Fuel Watch не переводятся.
- **`status_history` Benzonavt не подходит для истории прогноза.** Проверено на пяти станциях: ответ всегда содержит ровно два дня с посуточной гранулярностью (`day`, `status`, `confidence`, `fuels_now`) и без времени суток, а `reports_24h` — просто счётчик. Прогнозу нужно типичное местное время возобновления, которого там нет, поэтому эти поля не используются как источник истории.
- **`closed`/`closed_by_schedule` у 2GIS** осознанно не используются: интересует наличие 95-го, а не режим работы.

## Разбор противоречий внутри одного источника

У gdebenz видимый текст карточки и скрытое поле `fuels_now` перечисляют марки независимо и могут расходиться: 21 сентября 2026 года это было у 3 строк из 104 (например, `ул Глубокоовражная, 25` — карточка `92, ДТ · Очередь ≈5–20 машин` против `fuels_now = 92,95,ДТ`). Раньше адаптер объединял оба списка и получал ложный текущий сигнал АИ-95. Теперь марка, названная только одной стороной, даёт `UNCERTAIN` со структурным конфликтом (`kind: VISIBLE_VS_HIDDEN`, обе исходные формулировки сохраняются), и такой позитив не попадает в «Куда ехать». Прямой позитив другого источника по той же АЗС при этом остаётся в силе — конфликт локален для источника, который себе противоречит.

## Уверенность

`низкая`, `средняя` и `высокая` — это уверенность Fuel Watch в собственной оценке, а не заявленная источником вероятность. Она вычисляется из типа и свежести свидетельства, независимости provenance-групп, числа свежих прямых подтверждений и grade-specific активности. Адаптеры сохраняют доступные timestamps, конфликты и счётчики сигналов, но сейчас ни один из четырёх источников не даёт проверенного универсального confidence-поля с понятной и сопоставимой семантикой. Если такое поле появится, сначала нужно сохранить его как provenance и проверить калибровку; автоматически подменять им итоговую уверенность нельзя.
